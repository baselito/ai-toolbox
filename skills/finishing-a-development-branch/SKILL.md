# Finishing a Development Branch

## Overview

Guide completion of development work by presenting clear options and handling chosen workflow.

**Core principle:** Verify tests → Present options → Execute choice → Clean up.

**Announce at start:** "I'm using the finishing-a-development-branch skill to complete this work."

## The Process

### Step 0: Create Invocation Marker

**First action when this skill runs:**

```bash
Bash(mkdir -p ~/.claude && touch ~/.claude/.pr-skill-invoked)
```

This marker tells the `enforce-pr-skill` hook that this skill was actually invoked. Without it, `gh pr create` is blocked. The marker is single-use — the hook deletes it after allowing the PR creation.

### Step 0.5: Read the Actual Diff — MANDATORY

**Before writing any PR body content, read the actual changes:**

```bash
git diff <base-branch>..HEAD
git diff <base-branch>..HEAD --name-only
git log <base-branch>..HEAD --oneline
```

**⛔ DO NOT write the PR body from memory, training data, or the orchestrator's summary. ⛔**

Past failure: a PR body invented method names (`ToApiString` instead of the actual `ToAxonString`) and enum values (`Informational` instead of the actual `VeryLow`) because the subagent wrote from training data, not from the diff. The reviewer was confused; the ticket description didn't match the code.

Your PR body must be traceable to concrete evidence in the diff:
- Method/class names → verbatim from the diff, not paraphrased
- Test counts → grep the new test file for `[Fact]`/`[Test]`/`it(`/etc.
- File counts → from `--name-only` output
- Behaviour descriptions → read what the code actually does, don't assume

If you didn't read the diff, you cannot write a valid PR body. Stop and read it first.

### Step 0.6: Commit Any Pending Work — Delegate Message to Haiku

**If `git status` shows uncommitted changes, commit them BEFORE presenting options.**

```bash
git status --short
```

If there are uncommitted changes, the commit message MUST be generated by a Haiku subagent — not by the skill-invoking subagent (Opus) or the orchestrator (Fable). Writing commit messages on any higher tier wastes budget for a task Haiku handles well.

**Step-by-step — executable, not pseudo-code:**

1. **Capture the diff into shell variables** (these actual Bash calls must run first, BEFORE the `Agent()` call):

   ```bash
   STAGED_STAT=$(git diff --cached --stat)
   STAGED_DIFF=$(git diff --cached)
   UNSTAGED_STAT=$(git diff --stat)
   UNSTAGED_DIFF=$(git diff)
   ```

2. **Stage all changes** (so the commit captures everything):

   ```bash
   git add -A
   ```

3. **Build the Haiku subagent prompt by interpolating the captured diff content** — the `${VAR}` substitutions happen in your tool-call construction, NOT as literal text passed to Haiku:

   ```
   Agent(
     model: "haiku",
     prompt: "[DELEGATED] Generate a git commit message. Follow conventional commit format:

   - Subject line: type(scope): short summary, under 72 characters, imperative mood
   - Blank line
   - Body (1-5 lines): explain WHY (the reason for the change, not just what changed)

   Changes being committed:

   --- Staged stat ---
   ${STAGED_STAT}

   --- Staged diff ---
   ${STAGED_DIFF}

   --- Previously unstaged stat (now staged) ---
   ${UNSTAGED_STAT}

   --- Previously unstaged diff (now staged) ---
   ${UNSTAGED_DIFF}

   Return ONLY the commit message text — no markdown code fences, no commentary, no 'Here is the commit message'. End with exactly:

   Co-Authored-By: Claude Haiku <noreply@anthropic.com>"
   )
   ```

   The subagent returns the commit message as its response. Capture it into a shell variable — `COMMIT_MSG=$(...)` — using whatever mechanism the tool harness exposes for subagent results.

4. **Commit with the returned message via heredoc** (avoids shell quoting issues). Substitute `${COMMIT_MSG}` from step 3 into the heredoc body — do NOT leave the literal placeholder text in the command:

   ```bash
   git commit -m "$(cat <<EOF
   ${COMMIT_MSG}
   EOF
   )"
   ```

   (Note: heredoc delimiter is `EOF` without single quotes — this enables `${COMMIT_MSG}` expansion. Single-quoted `'EOF'` would disable expansion and pass the literal string `${COMMIT_MSG}` as the commit message, which is wrong.)

5. **Verify the commit landed:**

   ```bash
   git log -1 --oneline
   ```

**Haiku failure fallback:**

If the Haiku subagent returns empty, an error, or malformed content (e.g. missing the `type(scope):` prefix or the `Co-Authored-By` line), do NOT proceed with an empty or broken commit. Fall back to writing the commit message on the current subagent (Opus) for this one commit and note the Haiku failure in the response message so it can be investigated later. Better to ship a valid subagent-authored commit than to stall the workflow or create a broken commit.

**Do NOT write the commit message inline on the skill-invoking subagent or the orchestrator as the default path.** The /flow phase table says "All commits | Haiku" — this skill enforces that rule when it encounters uncommitted work. Writing it on the invoking subagent is a failure fallback, not the designed path.

**If there are NO uncommitted changes**, skip this step and continue to Step 1.

### Step 1: Verify Tests

**Before presenting options, verify tests pass:**

```bash
# Run project's test suite
npm test / cargo test / pytest / go test ./...
```

**If tests fail:**
```
Tests failing (<N> failures). Must fix before completing:

[Show failures]

Cannot proceed with merge/PR until tests pass.
```

Stop. Don't proceed to Step 2.

**If tests pass:** Continue to Step 2.

### Step 2: Detect Environment

**Determine workspace state before presenting options:**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# Capture the worktree path NOW, while the CWD is still inside the worktree.
# Options 1 and 4 later `cd "$MAIN_ROOT"`; after that, `git rev-parse` would
# resolve to the main repo. Step 6 REUSES GIT_DIR, GIT_COMMON, and WORKTREE_PATH
# and never recomputes them — otherwise the post-`cd` detection would wrongly
# report "normal repo" and skip cleanup. (CURRENT_BRANCH, captured just below,
# is for the Step 4/5 detached-HEAD path — Step 6 does not use it.)
WORKTREE_PATH=$(git rev-parse --show-toplevel)
# Detect detached HEAD: empty output means no current branch (detached).
# This must be captured here, before any cd, alongside the other state values.
CURRENT_BRANCH=$(git symbolic-ref -q --short HEAD || echo "")
```

These four values (`GIT_DIR`, `GIT_COMMON`, `WORKTREE_PATH`, `CURRENT_BRANCH`) are captured once here and carried forward to Steps 4, 5, and 6. This determines which menu to show and how cleanup works:

| State | Condition | Menu | Cleanup |
|-------|-----------|------|---------|
| Normal repo | `GIT_DIR == GIT_COMMON` | Standard 4 options | No worktree to clean up |
| Linked worktree, named branch | `GIT_DIR != GIT_COMMON` AND `CURRENT_BRANCH` non-empty | Standard 4 options | Provenance-based (see Step 6) |
| Linked worktree, detached HEAD | `GIT_DIR != GIT_COMMON` AND `CURRENT_BRANCH` empty | Options 2/3/4 (no merge) | No cleanup (externally managed) |

### Step 3: Determine Base Branch

```bash
# Try common base branches
git merge-base HEAD main 2>/dev/null || git merge-base HEAD master 2>/dev/null
```

Or ask: "This branch split from main - is that correct?"

### Step 3.5: Pre-PR Base Branch Verification (mandatory)

Before calling `gh pr create`, settle the target base branch. **Ask only when it is genuinely
unknown** — an unconditional per-PR confirm is the stopping `rules/autonomy.md` exists to remove,
and it fires hardest on the repo where consent is already recorded.

1. Read the target branch from the workflow context (set during the `/start` confirmation summary,
   or by any user instruction naming a target).
2. **Target KNOWN — do not ask.** State it and proceed: `Base: <branch> (from <where it came
   from>).` A target the user stated, or one recorded in `.claude/PROJECT.md`, is inferable, so it
   is not `Unknown` and the ask has no category.
3. **Target NOT known — resolve the repo's ACTUAL default branch and do not ask.** Read it from
   the repo rather than assuming `main`:

   ```bash
   gh repo view --json defaultBranchRef --jq .defaultBranchRef.name
   ```

   State `Base: <default> (repo default).` and proceed. The repo's own default is inferable, so
   this is not `Unknown` — and reading it is what makes the rule correct on a repo whose default
   is `develop`, `master` or anything else. If `gh` cannot answer (not authenticated, no remote),
   fall back to the checked two-step form below and, failing that, to the documented default
   `main` from `rules/git-workflow.md` → "Target Branch Awareness"; state which source was used.

   ```bash
   if fallback_raw=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null); then
     fallback="${fallback_raw#origin/}"
   else
     fallback="main"
   fi
   ```

   ⛔ **The `sed` is load-bearing, not tidying.** `git symbolic-ref --short
   refs/remotes/origin/HEAD` returns the REMOTE-TRACKING name — `origin/main`, not `main`
   (verified: it prints `origin/main` in this repo). Passing that to `gh pr create` `--base` names a
   ref that is not a branch of the repository, so the PR targets nothing valid. A fallback that
   silently yields a wrong-shaped value is worse than one that fails outright, because the caller
   has no signal to check. Strip the remote prefix before the value is used as a base.
4. **Ask (AskUserQuestion, header `Unknown`) in exactly two cases**, both of which are genuine
   non-inferability rather than routine confirmation:
   - the recorded constraint is a NEGATIVE one ("not main", "stay off develop") — those are not
     valid target values, so there is nothing to infer (`rules/git-workflow.md`); or
   - context was lost to compaction and the workflow context no longer holds a target the user
     had previously stated.

   "PR will target base branch: **[branch_name]**. Is this correct?"
   Options: "Yes, create PR" / "Change target branch" / "Cancel"
5. If the user changes the target, update it and proceed — no re-confirm.
6. Pass `--base [branch_name]` to `gh pr create` in Step 5.

NEVER create a PR without showing the base branch to the user first. This verification is mandatory even if the user already confirmed the target branch in `/start` — the constraint may have changed during implementation.

**Incident history:** TASK-760 — user said "only net8 and portal2", agent created PR #798 targeting main. Merged to main, required revert PR #799, 6 hours of rework.

### Step 3.6: Pre-PR Codex review (MANDATORY when Codex is enabled — hard-gated)

⛔ **"Codex enabled" = the memory flag ALONE — NOT "the CLI runs".** If
`~/.claude/memory.md` has `- Codex: enabled`, you MUST invoke the **`codex-review`
skill** on the final diff before opening the PR. Do NOT gate this on whether `codex
--version` runs: the `enforce-codex-review.sh` hook gates on the memory flag only, so
if you skipped the skill because the CLI happened to be down, the hook would block
`gh pr create` forever (enabled, but no marker) — a deadlock. Always invoke the skill
when the flag is set; the skill itself decides `reviewed` (CLI ran) vs `unavailable`
(genuine outage) and writes the matching marker. That keeps the skill and the hook in
lockstep.

This is NOT optional and NOT skippable: the `enforce-codex-review.sh` PreToolUse hook
**hard-blocks `gh pr create`** until the skill has recorded a review marker
(`.codex-review-complete` under the resolved state root — `$CLAUDE_STATE_DIR` when set,
`~/.claude` otherwise) for the current HEAD. No marker → no PR. (The
review is one local, read-only, automated-review-seeded adversarial pass; for `ai-engineering`
itself it adds a simplicity bias.)

- **Pass the confirmed base** — set `BASE=<the base branch confirmed in Step 3.5>`
  when invoking the skill so it reviews `$BASE...HEAD` (the real PR diff), not a
  hardcoded `main`. A PR targeting a non-main base must be reviewed against that base.
- **No-op ONLY when the flag is absent** — if `- Codex: enabled` is not in memory.md
  (e.g. a teammate who didn't opt in), the hook allows the PR and this step is skipped
  silently. When the flag IS set, the step is required and enforced.
- **The skill writes the marker** (its Step 4.5) AFTER applying any Codex-driven fixes,
  capturing the final HEAD. Do that before Step 5, or `gh pr create` is blocked.
- **One pass per PR** — apply valid findings via the normal fix path (LOC tiers),
  dismiss false positives with evidence, file out-of-scope items as follow-ups. Don't
  loop Codex.
- **Outage escape, not a skip** — if `codex exec` genuinely errors/times out, the skill
  records an `unavailable` marker for this HEAD so a real outage doesn't brick the PR.
  That path only fires after an actual failed attempt — it is never a silent skip.
- Quota / data-boundary policy: see the "Codex (optional cross-family collaborator)"
  section of `rules/performance.md`.

This step runs AFTER verification (Step 1) and base-branch confirmation (Step 3.5), and
BEFORE the PR is created in Step 5 (Option 2).

### Step 4: Present Options

**⛔ FIRST: is this an ask at all?** Two of the four options below — merging and discarding — are
`Irreversible` in the sense of `rules/autonomy.md`, and pushing/PR-creating is too on a repo with
no recorded consent. So this IS a category ask, not a checkpoint. But it is only an ask when the
answer is not already recorded:

- **Host permission consent for this repo** (the user-controlled permission layer names the repo
  and actions): the answer is option 2. Do NOT ask. Push, create the PR, and report it in the
  State block. The tracked `rules/git-workflow.md` table is historical documentation only.
- **Otherwise:** ask ONCE, using **`AskUserQuestion` with header `Irreversible`** — not a prose
  question. The tool call is what `enforce-ask-budget.sh` can see; a bare prose question is
  invisible to it and unenforceable, and an uncategorised tool call is denied outright for an
  opted-in developer. This step used to be written as prose with no header, so on the canonical
  `/flow` path it would either be denied or slip through ungoverned.

**Normal repo and named-branch worktree — present exactly these 4 options:**

```
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)
4. Discard this work

Which option?
```

**Detached HEAD — present exactly these options (using Step 5 canonical numbers):**

```
Implementation complete. You're on a detached HEAD (externally managed workspace).
Option 1 (Merge locally) is unavailable — there is no current branch to merge from.

2. Push as a new branch and create a Pull Request
3. Keep as-is (I'll handle it later)
4. Discard this work

Which option?
```

**Don't add explanation** - keep options concise. The numbers match Step 5 directly — the user types the same number that Step 5 executes. Do NOT renumber to 1/2/3.

### Step 5: Execute Choice

#### Option 1: Merge Locally

```bash
# Get main repo root for CWD safety — cd there first before any worktree ops
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# Merge first — verify success before removing anything
git checkout <base-branch>
git pull
git merge <feature-branch>

# Verify tests on merged result
<test command>

# Only after merge succeeds: cleanup worktree (Step 6), then delete branch
```

Then: Cleanup worktree (Step 6), then delete branch:

```bash
git branch -d <feature-branch>
```

#### Option 2: Push and Create PR

**Pre-flight checklist — confirm BEFORE running `gh pr create`:**

Read the PR body you are about to submit and verify it contains ALL of these exact section headings:

- [ ] `## Summary` — introductory bullets
- [ ] `### What this changes` — behaviour change, not a verb phrase like "adds tests"
- [ ] `### Why this matters` — business impact / risk reduced
- [ ] `### What was built` — specific details traceable to the diff
- [ ] `### Key decisions` — non-obvious choices (or "None" if truly none)
- [ ] `### Jira` — ticket ID and title (omit if no ticket)
- [ ] `## Test plan` — status lines with ✅ / ❌ / ⚠️ emojis

If ANY section is missing, go back and add it. A PR body with sections named differently (e.g. `## Structure`, `## Reviewer Notes`, `## Test Results`) is NOT compliant — it means the template wasn't loaded. Re-read this skill's Step 5 template and match it exactly.

**Additionally verify:**
- [ ] Method/class/variable names appear verbatim from the diff (grep-check them against the code)
- [ ] Test counts match actual `[Fact]`/`[Test]`/`it(` counts in the test files
- [ ] No content that you cannot point to in the diff or the ticket

Only proceed to `gh pr create` when every checkbox is confirmed.

```bash
# Detached HEAD: create a branch before pushing — no branch exists yet.
# $CURRENT_BRANCH (from Step 2) is empty in detached HEAD.
# Branch name follows git-workflow conventions: type/TICKET-slug
# (e.g. feature/DEV-1234-add-payment-flow). Derive from the ticket/work context.
if [ -z "$CURRENT_BRANCH" ]; then
  git switch -c <new-branch-name>   # e.g. feature/DEV-1234-slug-from-title
  CURRENT_BRANCH=<new-branch-name>
fi

# Push branch (works for both named-branch and newly-created-from-detached-HEAD)
git push -u origin "$CURRENT_BRANCH"

# Create PR with status indicators — ALWAYS pass --base from Step 3.5
gh pr create --base <target-branch> --title "<title>" --body "$(cat <<'EOF'
## Summary

<STANDARD: A reviewer who hasn't seen the ticket, the code, or the Slack thread
should understand this PR completely from the summary alone. Write for someone
joining the team next week.>

### What this changes
<Not "adds tests" or "fixes bug" — describe the actual behaviour change or addition.
What does the code DO? What can the system do now that it couldn't before?>

### Why this matters
<Business impact. What breaks without this? What risk does this reduce?
Who is affected — users, API consumers, other developers?>

### What was built
<Specific details a reviewer needs. For tests: what scenarios are covered,
what edge cases are tested, what's the coverage approach.
For features: what endpoints/components/services changed, what's the data flow.
For fixes: what was the root cause, what was the fix, why this approach.>

### Key decisions
<Anything non-obvious the reviewer should know. Design choices, trade-offs,
things that look wrong but are intentional. Skip this section if none.>

### Jira
<TICKET-ID> — <ticket title>

## Test plan

✅/❌/⚠️ <test count> new tests pass
✅/❌/⚠️ No regressions in existing <count> tests
✅/❌/⚠️ Build succeeds with 0 warnings
✅/❌/⚠️ Code review: Grade <A-F> — <key findings or "no issues">

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

**Status emoji rules for the Test plan section:**
- **✅** — verified and passing (agent confirmed with fresh evidence)
- **❌** — failed (something is broken)
- **⚠️** — warning (pre-existing failures, partial coverage, known limitations)

The agent MUST use the correct emoji based on actual results — not always ✅. If tests fail, use ❌. If there are pre-existing failures unrelated to this PR, use ⚠️ with explanation.

**Worktree preserved** — Option 2 keeps the worktree (the PR is open and may need follow-up commits). Cleanup happens later, on merge (Option 1) or discard (Option 4), never here. Do NOT run Step 6 for this option.

#### Option 3: Keep As-Is

Report: "Keeping branch <name>. Worktree preserved at <path>."

**Don't cleanup worktree.**

#### Option 4: Discard

**Confirm first — branch line is conditional on `$CURRENT_BRANCH` (from Step 2):**

When `CURRENT_BRANCH` is non-empty (normal branch):
```
This will permanently delete:
- Branch <name>
- All commits: <commit-list>
- Worktree at <path>

Type 'discard' to confirm.
```

When `CURRENT_BRANCH` is empty (detached HEAD):
```
This will permanently delete:
- (no branch — detached HEAD; discarding the detached commits + worktree)
- All commits: <commit-list>
- Worktree at <path>

Type 'discard' to confirm.
```

Wait for exact confirmation.

If confirmed:
```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

Then: Cleanup worktree (Step 6), then force-delete branch only if one exists:

```bash
# Delete the branch only if one exists (detached HEAD has none).
[ -n "$CURRENT_BRANCH" ] && git branch -D "$CURRENT_BRANCH"
```

### Step 6: Cleanup Workspace

**Only runs for Options 1 and 4.** Options 2 and 3 always preserve the worktree.

**Reuse `GIT_DIR`, `GIT_COMMON`, and `WORKTREE_PATH` from Step 2 — captured BEFORE Options 1/4 changed directory to `$MAIN_ROOT`.** Do NOT recompute them here: after the `cd "$MAIN_ROOT"` in the option block, `git rev-parse` resolves to the main repo, so a fresh `GIT_DIR`/`GIT_COMMON` would compare equal and wrongly report "normal repo — nothing to clean up", and a fresh `--show-toplevel` would return `$MAIN_ROOT` instead of the worktree.

**If `GIT_DIR == GIT_COMMON` (Step 2 values):** Normal repo, no worktree to clean up. Done.

**If `WORKTREE_PATH` (Step 2 value) is under `.worktrees/`, `worktrees/`, or `~/.config/superpowers/worktrees/`:** Superpowers created this worktree — we own cleanup. The option block already `cd`'d to `$MAIN_ROOT` (you cannot remove the worktree you are standing in), so remove it directly:

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # Self-healing: clean up any stale registrations
```

**Otherwise:** The host environment (harness) owns this workspace. Do NOT remove it. If your platform provides a workspace-exit tool (e.g. `ExitWorktree`), use it. Otherwise, leave the workspace in place.

### Step 7: Report PR metadata for orchestrator-side auto-poll decision

If Option 2 (Push and Create PR) was chosen, the PR is now open and reviewers (humans + automated-review bot) will leave comments over time. By default, the orchestrator schedules an auto-poll for new PRs, but **the skill does NOT emit the CronCreate call** — neither as a directive the orchestrator parses, nor as executable text in the final message.

**What the skill returns — trusted, minimal fields only** (no executable syntax, no CronCreate directives):

```
PR #<N> created — <URL>.
Auto-poll eligibility:
  pr_number: <N>            (from `gh pr view --json number` — trusted, echoed not derived)
  is_draft: <true|false>    (from `gh pr view --json isDraft`)
```

The orchestrator constructs the CronCreate call from its own trusted logic after the skill returns. See the **`pr-automation` skill** for the full orchestrator-side scheduling logic — the trust-boundary rationale, the validated-argument CronCreate construction, cadence, durability, and the merge-readiness gate specification; `rules/git-workflow.md` "Auto-Poll After PR Creation" carries the directive (and the reminder that the cron is best-effort, with inline handling as the reliable path).

**⛔ MANDATORY: Orchestrator auto-poll checklist (execute IMMEDIATELY after skill returns) ⛔**

The skill returns `pr_number` and `is_draft`. The orchestrator MUST execute this checklist in order immediately after the skill returns:

```
0. Append PR Created phase to handover.md (per rules/handover.md single-writer rule)
1. IF is_draft == false AND pr_number is valid AND NO_AUTO_POLL != 1
   AND CronList shows no existing "/review-pr" job for this PR number:
   a. Resolve OWNER/REPO: `gh repo view --json owner,name --jq '"$(.owner.login)/$(.name)"'`
   b. CronCreate(cron: "*/1 * * * *", prompt: "/review-pr --repo <owner>/<repo> <pr_number> --auto", recurring: true, durable: true)
      The --repo flag embeds the repo context in the cron prompt itself — no external state file needed.
      `durable: true` is part of the sanctioned call shape and is a DOCUMENTED NO-OP — it does
      not make the cron survive the session. Do not present this cron as the mechanism that keeps
      PR tending alive: it is idle-only, session-only, and the toolbox self-terminates it after
      1 day via the age check in `/review-pr` Step 0.5 — the same check that step b2 below writes
      the timestamp for. CronCreate's 7-day runtime cap is only the outer backstop, never the
      lifetime to plan around. The reliable path is the agent running `/review-pr` inline;
      session-surviving tending is a different trigger tier (a local scheduled task or GitHub
      Actions). Detail: the `pr-automation` skill → "Why the cron is best-effort, not reliable
      automation".
   b2. IMMEDIATELY after CronCreate returns (before parsing the response), write the creation epoch:
       date +%s > ~/.claude/.pr-<owner>-<repo>-<pr_number>-cron-created
       (WHY: the 1-day cap in /review-pr Step 0.5 relies on this timestamp. Writing it here —
        unconditionally, as soon as CronCreate is called — ensures the cap applies even if
        cron-id parsing fails later due to a response-format change. The cap triggers on
        scheduling-was-attempted, not on parsing-succeeded. Same composite key as cron-id.)
   c. Extract cron ID from response (grep -oE 'job [a-f0-9]{6,}' | head -1 | awk '{print $2}')
   d. IF cron ID is non-empty:
      - Save cron ID: echo "$CRON_ID" > ~/.claude/.pr-<owner>-<repo>-<pr_number>-cron-id
   e. IF cron ID extraction failed (empty): WARN user "auto-poll may not be active — verify with CronList". Do NOT write an empty cron-id file. (The cron-created file was already written in step b2 — leave it in place so the age cap can still fire.)
2. IF is_draft == true: skip auto-poll, tell user "Draft PR — auto-poll skipped. Run /review-pr <N> manually or undraft to enable."
3. IF NO_AUTO_POLL == 1: skip silently
4. Spawn jira-workflow-steward (Haiku) to post the PR Created comment.
   The delegation token already exists from workflow start (the orchestrator
   created it with `touch ~/.claude/.jira-delegation-token` at Step 0).
   Do NOT create a new token here — the token must come from the user-authorized
   orchestrator session, not from a delegated subagent.
5. Show the PR Created phase card (must include Jira: status line per rules/agents.md)
```

This is not optional. This is not "remember to do later." Steps 1-5 fire in order, atomically with PR creation. If the orchestrator shows a phase card without having executed this checklist, that is a compliance violation.

**Incident history:** TASK-747 PR #788 was created but auto-poll was not set up and no Jira comment was posted. The user had to remind the orchestrator despite a feedback memory explicitly saying "always set up auto-poll immediately after PR creation." Prose reminders are insufficient — this checklist makes the steps atomic with PR creation.

## Critical Rules

**Never:**
