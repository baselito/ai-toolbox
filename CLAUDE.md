# CLAUDE.md — Agent Instructions for This Repo

This file tells the agent what this repo is and how to work with it. Read this before doing anything.

---

## What This Repo Is

This is the **AI Engineering toolbox** — not a project. It installs agents, skills, commands, rules, and MCP connections onto a developer's machine so they are available in every project.

**This repo is never opened as a working project.** Developers clone it, run `./scripts/install.sh`, and then open their actual project repos. The agent reads this file only when someone is working on the toolbox itself (adding commands, updating agents, etc.).

## Install Stack (8 components)

1. **ECC** — `affaan-m/everything-claude-code` — full plugin. Provides 18 skills, rules, hooks, and 5 still-active agents (`architect`, `planner`, `doc-updater`, `harness-optimizer`, `loop-operator`). Seven of its review/execution agents were vendored into this repo so their tier could be raised to Opus and stay raised — see any of their file banners. (`chief-of-staff` was vendored into this repo — see `agents/chief-of-staff.md` — after upstream repurposed theirs into a comms-triage agent; it no longer counts toward the ECC total.)
2. **Superpowers** — `obra/superpowers` — 7 skills (brainstorming, systematic-debugging, using-git-worktrees, verification-before-completion, finishing-a-development-branch, test-driven-development, receiving-code-review). Full plugin is NOT installed.
3. **Agency agents** — `msitarzewski/agency-agents` — 8 agents (project-manager-senior, jira-workflow-steward, devops-automator, incident-response-commander, security-engineer, evidence-collector, reality-checker, api-tester). Plus 4 custom agents built for this repo (accessibility-auditor, performance-benchmarker, docs-lookup, chief-of-staff).
4. **GitHub CLI (`gh`)** — PRs, issues, code search, branch management. CLI-based (0 MCP tools). Always available. GitHub Actions pipelines are reviewed by the `devops-automator` agent via local YAML parsing.
5. **Seq MCP (optional)** — connect a user-managed log server for /incident, /bug, /perf; otherwise use local logs. No server or redaction service is bundled. See `docs/how-to/optional-integrations.md`.
6. **Atlassian CLI (acli)** — Jira ticket management via CLI. Uses API token auth (no OAuth). Confluence access dropped.
7. **Context7 MCP** — live library and framework documentation queries for the `docs-lookup` agent.
8. **Beads** — AI task tracking across sessions, post-mortems, sprint velocity.

**Hooks architecture:** The managed hook source is installed globally for every available provider. Claude receives hooks at `~/.claude/hooks/` and its merged `~/.claude/settings.json`; Codex receives the same managed hook files at `~/.codex/hooks/` and a translated `~/.codex/hooks.json`. The installer refreshes both surfaces from the same `hooks/hooks-config.json` source, preserves unrelated host configuration, and removes stale hooks previously managed by the toolbox. Each provider hook directory carries an ownership manifest; uninstall and refresh preserve Codex hooks and registrations when that proof is missing or empty instead of guessing. Config symlinks are preserved only when their targets remain inside the provider config directory. Per-project Claude overrides remain possible via `.claude/settings.json`.

**Delegation token pattern:** Hooks that guard Jira writes (`enforce-jira-delegation.sh`, `enforce-transition-script.sh`) use a token-file approach. The orchestrator creates `~/.claude/.jira-delegation-token` once at the start of a workflow; the hook checks the token exists and is < 3600 seconds old (session-level — NOT consumed on use). This replaces the broken transcript-based detection from earlier versions.

**Claude/Codex parity:** The durable `scripts/goal-loop` runtime and PR-poll
registration are provider-neutral. Claude and Codex use the same state, leases,
verification, mutation-testing policy, Jira steward boundary, and action journal. The active
provider is tried first and the other provider is used only for an explicit,
outcome-known `provider_unavailable` or `usage_limited` result. Unknown
outcomes remain pending for reconciliation so a provider is never retried
after work may have happened. Native host adapters differ: Claude uses slash
commands/hooks/CronCreate, while Codex uses the shared installed skills,
`~/.codex/hooks.json`, configured JSON wrapper, and a Codex Desktop heartbeat
registered through `register-pr-poll.sh`. The safety state and bounded execution contract remain
shared.

## Model Assignments (fixed — do not change)

Four tiers. A **named** agent's tier comes from its frontmatter — spawn it by `subagent_type` and pass no `model:`. An **anonymous** subagent (no `subagent_type`, or `general-purpose`) has no frontmatter, so it MUST carry an explicit `model:` or it inherits the session tier. Canonical rule: `rules/performance.md` → "The four tiers".

### Fable / GPT-6 Astra (planner-advisors — the thinkers)
- The main Claude Code session agent. Set via `"model": "fable"` in `~/.claude/settings.json`; the developer can override per session with `/model`.
- Coordinates phases, routes work, reads handover, spawns subagents, and reviews stalled or self-improvement incidents. Writes no feature code. GPT-6 Astra is the equivalent strategic advisor when the Codex provider is active.

### Opus — deep reasoning AND all review/execution

**Deep reasoning:** `architect` (ECC), `planner` (ECC), `security-engineer` (Agency),
`chief-of-staff` (this repo)

**Review (vendored from ECC so the tier sticks):** `code-reviewer`, `tdd-guide`,
`security-reviewer`, `database-reviewer`, `e2e-runner`, `refactor-cleaner`,
`build-error-resolver`

**Review/execution (ours):** `reality-checker`, `api-tester`, `devops-automator`,
`incident-response-commander`, `project-manager-senior`, `accessibility-auditor`,
`performance-benchmarker`

**Also Opus:** every anonymous `[DELEGATED]` subagent — discovery, brainstorming,
implementation, verification and PR creation. They have no frontmatter, so the spawn must
name the tier explicitly; all of them name `opus`.

### Sonnet — retrieval and capture only
- `docs-lookup` (custom, effort=low) — Context7 documentation queries
- `evidence-collector` (Agency, effort=low) — screenshot capture
- `harness-optimizer` (ECC), `loop-operator` (ECC) — ops monitoring, not review

### Haiku (fast, low-cost)
- `doc-updater` (ECC), `jira-workflow-steward` (Agency)
- Git commits, branch naming, Jira status moves
- Routine GoalRun reminders, heartbeats, and status/check-in messages use the lightest available model.

### Escalation
Both escalation targets are now the agent's own default, so the documented escalations are
no longer tier CHANGES — `project-manager-senior` is Opus outright, and a
`systematic-debugging` subagent inherits the orchestrator/Opus path. Kept here for history;
see `docs/reference/model-assignments.md` for the mechanism and its wiring gap.

## Agent Architecture — four roles

- **Orchestrator** — the main Claude Code agent (Fable, per `~/.claude/settings.json`). Persistent for the whole session. Coordinates phases, writes `.claude/handover.md`, spawns subagents. **Does NOT write feature code inline** — it spawns Opus subagents for that.
- **Chief-of-staff** (Opus, from frontmatter; see `rules/performance.md`) — decision-maker subagent. Ephemeral — runs, returns a plan, dies. Spawned TWICE per `/flow`:
  1. **Step 1.8 (Execution Plan):** Assigns agents and models for all phases based on the ticket
  2. **Step 9 (Code Review):** Selects which review agents run based on actual file changes
- **Implementing subagent** (Opus) — ephemeral subagent that writes the actual feature code in Phase 5. Spawned by the orchestrator with the `[DELEGATED]` marker.
- **Review agents** (Opus) — spawned by the orchestrator after chief-of-staff picks them. Read the diff, return findings. Never write production code.

See `docs/concepts/agents.md` for the full architecture, `docs/concepts/independence-principle.md` for why the split exists.

Not all agents run on every task — chief-of-staff activates only the relevant ones. Each agent runs on its own model (Opus/Sonnet/Haiku). <!-- tier-ok: generic tier enumeration, not a per-agent claim -->

### Always run (every task with code changes)
- `tdd-guide` (Opus), `code-reviewer` (Opus), `reality-checker` (Opus) — always last

### Conditional agents, parallel execution, and handover
"Conditional Agents" and "Parallel Execution" now live in the on-demand `agent-orchestration` skill — chief-of-staff selects agents based on file diff patterns from there. "Handover Protocol" stays in `rules/agents.md`.

## Provider-neutral operation

The toolbox has one shared workflow for Claude Code and Codex. Claude Code exposes
the workflow through the slash commands in `commands/`; Codex uses the same skills,
hooks, GoalRun state, and verification contract when its provider adapter is configured. `/start`
is the normal Claude Code shortcut. In Codex, the equivalent entry is a short natural-
language goal such as “Start the next Jira ticket and follow the toolbox workflow.”

Keep provider-specific host features explicit: Claude Code owns its slash-command
menu and CronCreate integration, while Codex uses its installed skill surface and
provider-neutral runtime/heartbeat. Do not create duplicate provider mirrors when a
shared skill or script can serve both.

## Working on This Repo

If you are modifying this toolbox repo:

1. **Commands** are in `commands/` — each is a Claude Code slash command in markdown format
2. **Agents** are in `agents/` — each has a `model:` field in frontmatter (do not change model assignments)
3. **Skills** are in `skills/` — each is a directory with skill files
4. **Rules** are in `rules/` — always-active baseline rules from ECC
5. **MCP configs** are in `mcp-configs/` — `mcp-servers.json` is the master config merged on install
6. **Scripts** are in `scripts/` — cross-platform bash scripts
7. **Docs** are in `docs/` — 46 files covering concepts, how-to guides, reference lists, and design specs
8. **Knowledge** is in `knowledge/` — learned-lessons knowledge file (`toolbox-lessons.yml`), human-gated, synced to `~/.claude/` by `sync-toolbox-lessons.sh`

Never add agents, skills, or rules that conflict with the existing install stack. Run `./scripts/verify.sh` after any changes to confirm nothing is broken.
